## 二、你必须作出明确研究判断

### 1. 先厘清两类的语义，不能把名字当定义

- 禁止做 A、没有义务做 A、允许做 A，是不同语义。不得把“not required to A”识别为
  “prohibited A”。明确无条件禁止、附条件禁止的首轮支持范围及排除条件。
- “如果 C，则必须 A”表示条件触发义务；它本身不推出“不满足 C 就禁止 A”。
  “只有 C 才能 A”才表达行为的必要前提。不得把所有 if 从句转换成 A→C。
- 核对旧 condition 数据和实现究竟在检查哪一种关系。若混淆，提出新版本的限定子类、
  新旧类型对应和 ineligible 原因；不改旧标签，不沿用旧 9/10 证明新定义有效。
- 明确判断对象：流程允许的行为还是实际执行日志；动作出现、可达、路径可执行不等价。
  分清 unknown（证据不足）与 not_applicable/unsupported（语义或模型不在支持范围）。
- 对这次最小试验选择一个具体、可实现的 BPMN 子集，说明 XOR/AND、循环、子流程、
  事件、默认流及动态条件状态如何处理。可以先限制范围，但不能默默忽略这些结构。

### 2. 决定值得实施的最小方法

逐类写出：问题定义 → 所需规则/流程证据 → 判定步骤 → 公式或伪代码 → 反例 → 能力边界。
若给公式，定义每个符号、量词、空集合及缺失输入语义，并说明哪些沿用前人、哪些是本项目设计。
公式必须对应真实机制；不能靠重命名、随意加权或条件字段有文字就声称创新。

重点检查：法规动作与流程节点绑定；条件的极性和作用域；动作是否可绕过必要前提；
不可达节点；条件节点只有相关文字却不控制动作；同义标签和非动作节点误匹配。
必要时输出证据路径或拒绝原因。不能把文本相似度直接当成逻辑满足度。
禁止动作未匹配到时，区分真的不存在与映射失败；不能一律宣布合规。

先看既有实现能复用什么、必须修正什么。若只有一类具备当前实现条件，明确选择先做该类，
另一类交付反例/缺口即可；不为同时做成两类而扩大为完整法律推理系统。
对条件、例外等前人已有概念不宣称首次；用原论文或官方研究资料核实最相近方法，标明核验范围。
本轮主线是独立抽取后的确定性检查，不恢复规则先行的 LLM 修复或 fallback。

### 3. 设计一次有信息量的最小离线试验

- 先复用旧预测和案例做机制诊断；新例子只作为独立版本的合成开发材料。首轮建议
  两类合计不超过 12 对合规对照/违规变体，另加少量必要反例；你给出最终数量和理由。
  小样例用于验证机制，不冒充独立泛化验证；暂不扩展约束、例外检测。
- 先冻结语义、案例资格、预期结果和规则，再评分。源条款族/基础流程的派生对象保持同组，
  不将同一模板的改名视为独立测试。AI 构造或判定明确标注，不伪称人工审核 Gold。
- 将人工/AI 构造规则输入的机制测试，与使用原始真实抽取结果的衔接诊断分表。
  不将理想规则输入上的效果归因给 LLM；缺少可复用真实预测的项目保持缺失。
- 若对比 Rules-Only 与 Direct-LLM，保持同流程、同适配、同检测器和阈值；若研究检测器
  改进，固定同一规则输入作前后对照。不要同时变多个因素后把收益归给一个因素。
- Sun/Winter 原生不支持的新增类型标 unsupported，不当成性能零；历史扩展实现按
  Sun-style/Winter-style extension 命名。是否需要新基线由研究问题决定，不自动多跑方法。
- 推理只访问法规/规则和流程输入；参考标签、target type、mutation、pair/control 标志
  及含答案的 ID/文件名不进入判定。评价器在预测冻结后才读目标字段和配对关系。
- 每类报告 TP/FP/FN/TN、positive/negative unknown、coverage、全配对成功率及全部分母。
  说明 unknown 如何影响指标，不能靠删掉 unknown 或失败样本提高成绩；对照只保证目标字段。
- 验收看语义与证据链是否正确、反例是否处理、结果是否可重现，不设必须超过历史分数的门槛。
  首轮完成一次冻结诊断后交付；不无限加规则、降阈值或反复试到正结果。

## 三、把约束和例外的难点解释清楚

分别解释“抽取错误”“映射错误”“表示不足”“流程没提供信息”“判定语义错误”“评价限制”，
不要全部归咎于 LLM 或不可观察性。至少包含以下说明性例子：

- 期限：72 小时从发现、发生还是其他事件开始计时？流程标注的 72 小时限制了哪个动作？
  数字相同但起点不同不等价；只有顺序和任务标签时无法证明期限满足。
- 约束异质性：时间、金额/数量、用途、法律引用不是同一种谓词，不能共享简单相似度判定。
- 例外：满足 E 时“无须通知”取消通知义务，不自动禁止通知；不适用义务与违反义务分开。
  需要确定 E 是否成立、针对哪个动作、如何影响路径及与其他规则的优先关系。
- 实际失败链：约束曾因把例外说明节点错当动作而误报，guard 只能纠错到 unknown；
  例外案例的 action 曾是“referred to”，映射和原文抽取也有问题，不可单凭匹配器没找到就
  断言流程绝无相关动作。历史报告的诊断标签须结合规则原文和流程实际标签复核。

说明哪些问题可以由局部修复解决，哪些需要新的流程信息/类型化表示；它们难不代表永远不可做。
