# S3-RECONSTRUCT：可检查的三类基准草案与执行边界

2026-09-23。此文件是具体实验协议说明，不是论文正文或新的全项目状态页。

## 已构造的输入与参考

`configs/stage3_reconstruction_v4.json` 固定选取依据、适用前提、流程标签和变体操作。
`data/development/stage3_reconstruction_v4/manifest.json` 绑定来源、代码及所有输出。
原文来自只读继承包，保存文件 SHA、原文字符位置和义务/主体/顺序证据位置。
法规原文可对照 [EUR-Lex GDPR](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng)。

| 条款 | 控制者必须完成的活动 | 原文要求的后续事件 |
|---|---|---|
| 13(3) | 告知新目的及相关补充信息 | 进一步处理直接取得的个人数据 |
| 14(4) | 告知其他目的及相关补充信息 | 进一步处理间接取得的个人数据 |
| 18(3) | 告知本人将解除处理限制 | 解除处理限制 |
| 35(1) 首句 | 开展数据保护影响评估 | 开始相关高风险处理 |
| 36(1) | 咨询监管机关 | 开始相应处理 |

每项有 1 个基准、1 个删除必需活动变体、1 个错误执行者变体、1 个交换先后变体，
共 20 个 BPMN（5 基准、15 违规）。五个来源要求才是独立来源数；不能将 20 个
变体说成 20 个独立真实流程。13(3)/14(4)表述相似，泛化范围尤其有限。

错误执行者同时写入 BPMN participant 与 process.name，两个字段表示同一执行主体，
分别供 Sun 与原生 Winter 解析器观察；不是只改一条 lane 内活动。只在声明的单项义务
范围内证明一个语义错误，未评价的整篇条文或整部 GDPR 不宣称全部合规。

缺少必需活动时，执行者和先后检查的参考状态为 `not_applicable`，不是负例。
因此每方法固定评价 50 项：缺活动 20、错误执行者 15、顺序 15；共 15 阳性、35
阴性。另 10 项在看到预测前就确定不适用。不因预测错误、unknown 或分数极端删项。
真实 unknown 保留，阳性上的 unknown 计漏报；阴性上 unknown 不宣称已确认合规。

参考是 AI 根据条文解释并通过确定性变体构造的 `construction_reference`，
`is_gold=false`、`human_adjudicated=false`。结构测试只能确认 XML、变化范围和
设定参考一致，不能冒充独立人工法律审核。旧 Gold 与已完成审核均不改。

## 与 Sun 及原表三设想的区别

沿用“补充基准 → 删除活动/改执行者/交换活动”的实验构造思路，当前仅针对以上
五项明确义务；不是 Sun 作者的四流程、46 篇法规实验复现。原始补充基准及答案
没有提供。更广的完整 GDPR 端到端 F1 仍需另外建立完整适用性与多标签参考。

计划表三为已指定适用条款范围内的 checking P/R/F1。推理仍为每个当前 BPMN
计算全部五项法规的预测，再由独立 evaluator 读取范围与参考。它不是自动规则选择
的端到端分数；不使用 `matching_score > tau` 外层门槛，不自造 Top-K。匹配分数
可以保存；没有独立完整相关性答案时不生成 MAP 或把未标条款当负例。

Sun/Ours 共享 Stage 1 表示、Stage 3 评分、阈值和转换。Winter 走原有独立实现。
保留 `unknown` 及原因、各类型分数与微平均分数、TP/FP/FN 明细；没有 Ours 专属
补全、不读取 control 辅助推理、不按希望的排名改答案、不修改 F1。

## 当前不能直接运行正式表三的实现缺口

现行 Rules-Only `estg150_b0_development_v10.py` 的组合函数硬编码
`order_relations: []`。这不只是旧 74 句碰巧无关系；该版本对任何新句都会为空。
当前冻结转换器只透传显式边，因此直接补数据仍无法检验完整 Sun 三类能力。

Direct-LLM v6 允许输出有原文依据的顺序边，但仅允许同 clause 的 action ID 端点；
时间条件中名词化的“processing”能否在其抽取与转换中保留，尚需真实预测检验。
不能把这一风险隐藏成“新调用必定解决顺序”。需要先确认共同 Rule Record 接口的
顺序信息路径，以及 Sun 重建中的实际顺序抽取机制，才可解除三类正式运行阻断。
不把后加规则冒称 Sun 原实现，也不在旧方法名字下悄悄替换算法。

本草案先于新预测固化。新增调用只针对五个选中原文输入，旧 74 句不重跑。
API 请求与价格预算另列；当前未获新 API 授权，未产生表三数值。

## 2026-09-24 冻结 B0 的真实抽取核查

`data/predictions/stage3_v4_b0_frozen_v1/manifest.json` 记录本地运行，耗时 22.973 秒。
五个输入全部返回且都包含义务 clause；无 LLM/API。预测先持久化，未计算 Stage 3
F1，也未据此改参考答案或挑选来源条文。

| 条款 | 动作数 | 主体数 | 时间等约束数 | 直接顺序边数 |
|---|---:|---:|---:|---:|
| 13(3) | 2 | 2 | 3 | 0 |
| 14(4) | 2 | 2 | 3 | 0 |
| 18(3) | 1 | 1 | 2 | 0 |
| 35(1) | 1 | 1 | 3 | 0 |
| 36(1) | 1 | 1 | 1 | 0 |

直接查看 source-offset 可确认：13/14 的动作之一仅为 provide，另一个是包含
intends 的较长短语；18 的动作把 before 约束一并带入；36 的动作跨入 where 条件。
这些是冻结抽取器的实际输出问题，不能以人工动作或新参考代替它们去评分。

可读作者稿将 before/after 列为 constraint 标记，但没有可恢复的完整 Ur 生成
实现。拟补充双方共用的预测约束到顺序端点转换，保持 Sun 评分与阈值；明确为
独立重建补充，不能假称找回原代码，也不能把时间端点增为新的强制义务。
已向用户提交该具体方法口径问题，未批准前不将此补充接入正式方法。

这一补充的形式化差异也必须写明：作者稿将 Ur 的端点定义在动作集合 Ar 中，
而“prior to the processing”中的名词化事件可能只存在于预测 constraint，不在
预测 actions 中。若将它作为顺序端点、又不把它新增为必需活动，就扩展了现行
转换器可接受的端点来源。它不是单纯修复一个丢字段问题，也不应称为与作者稿
所有定义完全一致。用户可以据此判断是否接受该共同投影的独立重建口径。

### BPMN 执行者表示修复

原生 Winter 从 process.name 取得执行者，Sun 从 participant 取得执行者；初稿
漏了前者。2026-09-24 在任何 Stage 3 评分前为 20 个模型同步这两个名称，并用
双方实际解析器验证控制与变体都得到同一个执行主体。只修模型表示，来源、参考
标签、成员、流程顺序与已完成 B0 输入/预测保持不变。旧草案由 Git 检查点保留。

第一次实际解析器测试暴露第二个表示问题：Winter 的 minidom 路径匹配无前缀
`process/task` 标签，带 `bpmn:` 前缀时会得到空流程。新构造现统一为与官方原始
BPMN 相同的默认命名空间（namespace URI 不变），不修改 Winter 算法。失败检查
记录保留；修正后重新验证本批相关测试，不扩大到全量测试或拿空流程计算 F1。
